# 07. 모델 독립 AI와 Tool Gateway

상태: 상세 설계 채택안. Orca는 의존하지 않는다. 특정 provider 지원 완료를 뜻하지 않는다.

## 기능과 분류

AI-01 backend 설정·capability, AI-02 main AI, AI-03 item AI/Skill 로딩, AI-04 공통 tool 실행, AI-05 결과 검증, AI-06 감사 로그·데이터 전송 정책. 공통 점검 엔진 기능이다.

## 역할과 경계

main AI는 선택된 run plan을 읽고 항목 실행을 지시하며 종료/hang/오류 상태와 최종 근거를 검토한다. item AI는 공통+해당 platform Skill을 따라 한 항목만 수행한다. 각 item은 독립 context이며 다른 run의 비밀·증적을 자동 참조하지 않는다.

실제 동시성·허용 범위·취소·최종 상태 전이는 Python scheduler가 통제한다. main AI가 범위 밖 check를 추가하거나 target을 바꾸거나 cleanup 확인 없이 다음 항목을 강행할 수 없다. AI의 설명과 tool 실행 성공은 구분한다.

## Provider adapter

공통 계약: `start_job(context, tool_catalog)`, `stream_events(job_id)`, `cancel(job_id)`, `get_result(job_id)`, `capabilities()`.

모델 API adapter와 agent CLI adapter를 별도 구현한다. Claude Code/Codex는 에이전트 runtime, GLM은 모델일 수 있으므로 같은 native capability를 가정하지 않는다. 로컬 모델은 공통 Python tool loop를 사용할 수 있다.

capability: tool calling, structured output, streaming, cancellation, resume, local-only, gateway enforcement mode. provider/model/runtime version과 configuration hash를 run snapshot에 남긴다. 지원하지 않는 capability는 숨기거나 모방 성공으로 표시하지 않는다.

Backend connection test는 인증/응답/schema/tool bridge/cancel 테스트를 구분한다. 단순 텍스트 응답 성공만으로 device inspection ready를 표시하지 않는다. 초기에는 fake provider로 계약 검증 후 하나의 실제 provider를 붙이고 두 번째 provider로 교체 가능성을 검증한다. 우선 provider 선택은 실제 환경·인증 가용성에 따라 PoC에서 결정한다.

## Gateway 강제

도구 요청에는 run/check/tool-call ID, owner+fencing generation, operation, typed args를 둔다. Gateway는 scope, capability, schema, device lease, deadline, cancellation state를 검증한다. 반환값에는 실제 실행 여부, 시작/종료, 결과/오류, evidence refs가 들어간다.

임의 shell/ADB 직접 실행을 기본 tool로 제공하지 않는다. CLI backend가 자체 shell을 가지고 있다면 단순 '사용하지 말라' 프롬프트는 충분하지 않다. worker가 device/ADB/network replay 자원에 직접 접근하지 못하고 Gateway만 사용할 수 있는 OS/process 권한 경계를 검증해야 한다. 이를 증명하지 못한 CLI는 device-mutating mode에서 unavailable로 두며, 저장된 증적의 read-only 분석도 별도 sandbox로 제공 파일만 읽고 다른 로컬 파일·device·network mutation에 접근할 수 없음이 입증된 경우에만 허용한다. 이를 입증하지 못하면 read-only를 포함해 unavailable이다. 실제 경계 구현 방식은 host별 PoC 게이트다.

Tool catalog는 device/app, route/replay, packet query/replay, static analysis, evidence의 typed operations로 구성한다. IDOR/replay는 사전 정의 QA 범위와 변경·복원 계약을 검증한다. 모델이 임의 endpoint나 계정을 만들어 전송할 수 없다.

## Skill와 입력 context

Skill은 최대 common/AOS/iOS 세 개다. 실행시 파일 내용을 snapshot하고 hash를 저장한다. manifest requirements와 Skill 설명이 충돌하면 실행 전 차단한다. Skill은 외부 도구 결과보다 높은 신뢰의 제품 절차지만, 현재 run scope를 확장할 권한은 없다.

Context에는 목적/선택 variant/기기·앱 snapshot/route·packet 목록/coverage/도구 목록/판정 schema를 전달한다. 전체 APK나 전체 packet payload를 일괄 prompt에 넣지 않는다. 필요한 참조를 Tool Gateway로 조회한다.

패킷, 화면 OCR, 앱 문자열, 분석 출력은 신뢰하지 않는 검사 데이터다. 그 안에 있는 지시문을 agent 지시로 실행하지 않는다. 모델 output을 tool call로 적용할 때 항상 typed validation을 거친다.

## 결과와 감사

결과 필드: run/check IDs, execution status, verdict, reason, evidence refs, tested scope, limitations, timestamps, version hashes. 판단 불가능은 reason 필수다. 양호/취약에는 기대 증거와 절차 완료 조건이 있어야 한다. evidence가 빠진 양호를 통과시키지 않는다.

Schema 오류는 최대 한 번의 제한된 수정 요청을 허용한다. 계속 오류이면 판단 불가능으로 마무리하고 사용자에게 표시 가능한 최종 응답 내용만 증적으로 남긴다. credential/비밀값은 제거하고 provider의 hidden reasoning 또는 사고과정 필드는 저장하지 않는다. schema repair는 tool catalog가 비어 있는 제한 작업으로 수행하며 기기 테스트·tool 재실행을 허용하지 않는다.

로그는 요청한 도구·안전한 입력 요약·실제 실행 결과·오류·취소·증거·판정 이유를 남긴다. 숨겨진 사고과정은 요구하거나 저장하지 않는다. live log는 점검 탭, 최종 근거는 결과 로그 탭에 표시한다.

## 데이터와 비용 경계

로컬 provider와 외부 provider의 데이터 목적지를 구분한다. project별 외부 전송 허용 필드/secret reference resolution 정책을 실행 전에 고정한다. egress 검사는 초기 prompt뿐 아니라 tool 결과, 오류 문자열, 첨부/이미지, 재시도/repair context, CLI 출력 등 provider로 가는 모든 채널에 적용한다. secret reference는 executor 내부에서만 해석하고 해석된 비밀번호/token/key를 모델에 반환하지 않는다. 실제 인증정보·키·고객 데이터는 기본적으로 전송하지 않는다. 원본 payload 필요 시 허용된 필드 범위에서 제공하며, 허용되지 않으면 판단 불가능 이유로 남긴다. 마스킹 버튼을 추가하지 않는다.

step/tool call/토큰 또는 비용 예산, item/run deadline을 설정한다. provider가 비용을 보고하지 않으면 정확한 금액으로 표시하지 않는다. context limit 초과는 필요 데이터 조회 범위 축소로 처리하고 보이지 않는 부분을 검증한 것처럼 쓰지 않는다. rate limit/인증 실패/네트워크 오류는 backend 오류로 분리한다.

## 인수 기준

1. 두 provider가 같은 run/result/tool schema를 사용한다.
2. 지원되지 않는 cancel/gateway capability backend는 device execution을 시작하지 않는다.
3. 범위 밖 tool/target, stale fencing token, 취소 후 tool 요청이 거부된다.
4. 악성 지시문을 포함한 packet fixture가 tool scope를 확장하지 않는다.
5. 증거 없는 양호 및 잘못된 결과 schema가 최종 결과에 그대로 들어가지 않는다.
6. main crash와 item crash의 실행 로그·상태가 분리된다.
7. tool loop 예산 소진은 이유 있는 판단 불가능으로 종료되고 무한 반복하지 않는다.
8. 외부 전송 금지 secret fixture가 provider 요청에서 발견되지 않는다.
9. 로그에는 숨겨진 사고과정 대신 관측 가능한 실행 근거가 남는다.
10. tool 오류/첨부/repair 경로에서도 비밀값이 유출되지 않으며 repair가 tool을 실행하지 못한다.
11. 격리 검증에 실패한 CLI는 read-only라는 이름으로 우회 활성화되지 않는다.

## 검증 게이트

각 SDK/CLI/API의 현재 공식 인증·embedding·tool·cancel 방식과 약관을 구현 전에 검증한다. 현재 설계가 특정 버전의 지원을 보증하지 않는다. host별 gateway 강제, provider 프로세스 종료, structured output·rate limit, 로컬 모델 최소 성능을 독립 PoC로 확인한다.
