# 09. 평가항목 18개 커버리지와 분리형 PoC 게이트

관련 기능: F-25~29, F-17, F-24, F-31, F-39. 사용자 제공 표의 18개 행을 하나도 버리지 않고 내부 카탈로그에 매핑한다. **공식 평가기준 원본의 식별자·적용 플랫폼을 이번 검토에서 재검증하지 못했다.** 따라서 아래 `CHK-*`는 제품 내부 ID이며 금융보안원 공식 ID가 아니다. 기존 문서의 ‘모바일 13개/HTS 계열 5개’ 분리는 provisional이고, 원본 대조 전 공식 범위 확정으로 표현하지 않는다.

## 1. 분류와 구현 상태의 의미

- E→S→U→N은 구현 우선순위다. 실행 순서, 공식 위험등급 또는 자동화 가능 정도와 다르다.
- 한 항목은 primary 분류 하나와 보조 capability 여러 개를 가진다. 업데이트 확인에 실행 관찰이 필요하다는 이유로 static 도구만 고집하지 않는다.
- `초기 E`, `후속 S/U/N`은 해당 단계의 구현 후보이며 지금 모든 항목 자동화 완료를 약속하지 않는다.
- `M/보조`는 수동 증적 제출·확인으로 보완한다. 자동 관찰과 수동 진술을 분리 저장한다.
- `모바일 확장`은 사용자가 요청한 기능을 버리는 것이 아니라 공식 모바일 평가항목과 구분하는 내부 점검이다.
- 미구현/필수조건 미충족 항목은 목록에 남기고 비활성 이유를 보인다. 실행할 수 없는 항목을 양호로 만들지 않는다.

## 3. 각 항목에서 아직 결정해야 하는 fixture 상세

현재 설계에서 확정할 수 있는 것은 입력·출력·필요 증거 경계다. 앱과 보안 모듈에 종속된 값은 PoC 직전 테스트 프로필로 정한다.

|항목군|미확정 값|값이 없을 때 동작|
|---|---|---|
|CHK-01|QA 인증 수단, 유효시간/폐기 상태, 거래 완료 oracle|해당 subcase 비활성 또는 판단 불가능; 모델이 만료 정책을 추측하지 않음|

|CHK-05~06|변경 적용 확인/복원, 재사용 이력 범위·정책|검증 범위 제한 또는 수동 보완, 실제 비밀번호 저장을 예제에 넣지 않음|

## 4. 항목별 최소 판정 규칙

다음은 제품 검사 절차의 최소 규칙이며 공식 판정 해석의 확정을 대신하지 않는다. 각 rule은 선택한 variant의 명시적 시험 범위에 한정한다. 취약 조건이 입증되면 취약이 우선하고, 그렇지 않으면 모든 필수 scope의 방어 확인이 있어야 양호다. 일부만 관찰하면 판단 불가능이다.

|---|---|---|---|

## 5. 항목 manifest 및 Skill 최소 계약

```text
checks/CHK-07/
  manifest.yaml
  common/SKILL.md
  aos/SKILL.md        # 필요할 때
  ios/SKILL.md        # 필요할 때
```

Skill은 최대 3개. manifest·fixture·Python 도구는 Skill 개수에 포함하지 않는다.

manifest 필수 정보:
- `check_id`, `title`, `source_reference`, `source_scope_status`(provisional/verified), `official_id?`
- `implementation_group`, `supported_platforms`, `implementation_status`
- `schema_version`, `skill_version`, 공통/플랫폼 Skill content hash
- `requirements`: device/root/OS/tool/artifact/route/packets/profile/evidence 입력
- `steps` 또는 Skill 절차 참조, fixture schema, `expected_evidence`, `pass_rule`, `fail_rule`, `inconclusive_rule`
- timeout, cancel, cleanup, side-effect/idempotency 정책 및 초기 상태 검증

공통 Skill은 판정 의미·필수 증거·실행 범위·기대 종료/정리 조건을 정의한다. 플랫폼 Skill은 해당 플랫폼 도구·관찰 경로만 구체화하며 공통 판정 기준을 조용히 완화하지 않는다. 충돌/누락은 load-time 오류다. 실행 agent는 현재 플랫폼의 Skill만 common과 함께 읽는다.

## 6. 단일 기기 검사 절차 공통 틀

1. preflight: 지원 상태·필수 fixture·실제 device capability·앱/기록 일치 검사.
2. baseline: 절차별 통제 조건을 확인한다. 동적·거래 절차는 앱/보호 서비스·계정·서버 초기 상태를 확인한다. 정적 artifact-only 절차는 파일 식별·hash·분석 범위·도구 readiness를 확인하며 불필요한 앱 실행이나 거래 oracle을 요구하지 않는다.
3. observation/action: Skill에 정한 도구를 gateway로 실행하고 attempt/result를 기록.
4. verification: 항목 정의에 맞는 oracle을 대조한다. 거래/권한 절차는 실제 서비스/데이터 상태, 정적 절차는 분석 산출물과 해당 판정 기준을 사용한다.
5. result: 검증한 범위·한계·evidence 참조와 세 가지 판정 중 하나를 제출.
6. cleanup: 변경 앱/프로세스/기기/QA 데이터를 계약대로 복원하고 결과를 확인.
7. cleanup 실패/상태 불명은 다음 항목을 진행하지 않는 원인이 될 수 있다. 이미 수집한 결과와 미수행 항목을 보존한다.

## 7. PoC 분리와 통과 게이트

독립 프로그램은 같은 최소 JSON 계약을 공유하되 GPUI나 main AI가 없어도 실행 가능해야 한다. 지금 단계는 설계이며 실제 구현·기기 테스트는 시작하지 않는다.

|PoC|검증할 기능|입출력|필수 시험|통과 후 결정|
|---|---|---|---|---|

P1의 기존 제안 수용기준은 동일 초기 상태의 합성 QA 앱 10단계 route를 3회 모두 목표 상태로 재생하는 것이다. P2는 식별 가능한 20개 메시지를 누락·중복 없이 추적한다. 이 수치는 초기 검증용 설계 기준이며 모든 앱/트래픽의 신뢰도를 증명하지 않는다. 앱별 timeout/성능 한계는 측정 결과와 함께 확정한다.

### CHK-07 첫 E 항목 예시

- 순정 단말은 정상 서비스 baseline을 확인하지만 변조 탐지 기능의 양호 판정을 단독으로 만들 수 없다.
- 변조가 확인된 단말에서 기대 서비스 차단 및 관련 증거를 확인하면 해당 시험 범위에서 양호.
- 변조된 단말에서 보호 대상 서비스가 실제 이용 가능함을 입증하면 해당 시험 범위에서 취약.
- root 상태 미확인, 앱 설치 실패, 로그인/서비스 확인 동선 없음, 앱 crash 원인 불명은 판단 불가능.
- 단순 ADB package launch는 앱 시작 관찰이다. 검증하려는 서비스 이용 여부를 입증하지 못하면 전체 검사 완료로 간주하지 않는다.

## 8. 도출·분류·설계·평가의 완료 조건

- 18개 항목 모두 내부 ID가 있고 초기/후속/확장/수동/제외 이유가 있다.
- 18개 항목의 필수 입력·증거와 양호/취약/판단 불가능 최소 규칙 정의를 완료했다. 각 앱·보안 모듈별 fixture와 관찰 oracle의 실제 유효성은 PoC 검증 게이트로 남긴다.
- 원본 식별자 확인, 실제 도구 호환성, 고객 앱 fixture는 닫히지 않은 검증 게이트로 명시한다. 문서 검토 완료와 실제 PoC 완료를 혼동하지 않는다.
- 새로운 기능이 필요하지 않은 상태와 모든 기술 불확실성이 사라진 상태는 다르다. 기능 도출은 수렴할 수 있고 PoC 게이트는 남을 수 있다.
- iOS/웹 구현, HTS 구현, 실제 malware 실행, 임의 인증 우회, 모든 TLS/protocol 자동 해석을 이번 MVP 범위로 추가하지 않는다.
