# 07. 분리형 PoC 계획

## 1. 사용자 결정과 제안의 경계

**확정 방향**: 설계를 어느 정도 정리한 뒤 기능별로 독립된 작은 프로그램을 만들어 검증하고, 나중에 연결한다. Appium 동선 기록/재생, RECORD/STOP 기반 패킷 표시, 평가항목별 Python 점검 스크립트가 분리 대상이다.

**이번 변경은 문서만 작성한다.** 아직 PoC 구현·기기 조작·검사 실행을 시작하지 않는다. 아래 단계, 인터페이스, 횟수와 수치는 설계 제안이며 확정 기준으로 간주하지 않는다.

독립 PoC는 최종 제품의 모듈 후보이다. 단순 임시 코드 묶음을 만들어 나중에 전면 재작성하기보다는, 작고 교체 가능한 입출력 경계부터 맞춘다. 다만 최종 GUI나 AI 오케스트레이터를 먼저 완성해야 개별 검증을 할 수 있게 만들지 않는다.

## 2. 시작 조건과 공통 최소 계약

각 PoC 시작 전에 한 장의 실행 명세를 준비한다:
- 확인하려는 가설과 제외 범위
- QA 앱/기기 상태 및 필요한 도구
- 입력·출력 예시, 실패·취소·정리 동작
- 재현 가능한 시험 시나리오와 통과 기준
- 결과 증적 위치 및 다음 단계에 넘길 결정

공통 제안:
- 내부 경계는 versioned JSON 파일 또는 구조화 이벤트로 시작한다. API/RPC 방식은 통합 때 선택한다.
- 명시적 device ID와 package ID를 받는다. '첫 번째 USB 기기'를 암묵적으로 사용하지 않는다.
- session_id/run_id, event_id, timestamp, schema_version을 공유한다.
- 비밀값은 로컬 참조로 주입하고, repo에는 합성 fixture와 문서만 둔다.
- 각 PoC는 자기 실행·정리 책임을 갖는다. 실제 기기는 한 대이므로 서로 독립된 프로그램이어도 동시 조작하지 않는다.
- 성공/실패/취소 등의 실행 상태와 양호/취약/판단 불가능 판정을 분리한다.
- 문서의 schema는 잠정 계약이다. 첫 시험 결과에 따라 변경 이력을 남기고 수정한다.

## 3. 단계별 계획

### P0. 공통 계약과 시험 fixture

목적: 각 조각이 같은 기기·앱·기록·증적을 식별할 수 있게 한다.

입력: 시험 기기/앱 설정, 동작 시나리오, 합성 packet 및 result 예시.
출력: 최소 schema, 예제 파일, 독립 실행/종료 방법, 검증 체크리스트.

통과 기준 제안:
- 예제 입력/출력이 schema 검증을 모두 통과한다.
- 잘못된 필수 필드, 지원하지 않는 schema version을 명확한 오류로 거부한다.
- 예제와 저장소에 실제 비밀번호/token/고객 데이터가 없다.

### P1. Appium 동선 기록·재생

목적: PC에서 조작한 입력을 재현 가능한 동선으로 만들고 선택한 실제 Android 기기에서 재생한다.

입력: device ID, package ID, 기록 시작/종료 명령, PC 표시 화면의 입력.
출력: route JSON, 단계별 이벤트, 필요한 screenshot/UI tree 참조, 재생 결과.

경계:
- 입력 캡처 계층과 Appium 실행 계층을 구분한다.
- 미러링 화면에서 발생한 임의 입력이 Appium에 자동 기록된다고 가정하지 않는다. recorder가 소유한 입력 경로 또는 명시적 이벤트 전달 경로를 먼저 검증한다.
- 탭, 스와이프, 텍스트 입력, 뒤로 가기, 대기 조건을 작은 범위부터 검증한다.
- 좌표만 저장할지 locator를 우선 사용할지는 PoC 결과로 정한다.
- 기록이 없을 때의 package launch도 별도 시나리오로 검증한다.

통과 기준 제안:
- 합성 QA 앱에서 사전에 정한 10단계 동선을 동일 초기 상태로 3회 재생하여 세 번 모두 기대 종료 상태에 도달한다.
- 세 번의 모든 단계가 action ID와 성공/실패 결과를 갖는다.
- 연결 해제나 locator 실패 시 멈춘 단계와 이유를 표시하고 뒤의 단계를 성공으로 기록하지 않는다.
- STOP 이후 새 입력을 기존 recording에 추가하지 않는다.
- 취소 후 실행 중 기기 명령이 남아 있지 않음을 확인한다.

의존성: P0, Appium과 기기 제어 환경. 최종 GPUI 화면이나 AI는 필요 없다.

### P2. 패킷 수집·RECORD/STOP·표시

목적: 기존 Hawkeye relay를 참고하여 GUI/AI와 독립된 전달 경로, 기록 경계, 패킷 조회를 검증한다.

입력: relay 설정, 선택 기기/대상 연결 설정, recording ID, RECORD/STOP, proxy ON/OFF.
출력: 영속 packet 기록, 건수/목록/상세 조회, relay 상태와 오류 이벤트.

경계:
- 처음에는 간단한 독립 화면 또는 CLI로 검증할 수 있다. 최종 GPUI 레이아웃 확정이 선행조건은 아니다.
- STOP은 기록 중단, proxy OFF는 릴레이 중단으로 구분하는 방안을 시험한다.
- STOP 순간 진행 중이던 메시지의 귀속, OFF 시 활성 연결 정리 정책을 명시한다.
- TCP chunk 수를 논리적인 요청 건수와 같다고 간주하지 않는다.
- 지원하지 않는 protocol은 명시하고 HTTP/2·HTTP/3·QUIC 지원을 추정하지 않는다.

통과 기준 제안:
- 지원 protocol의 식별 가능한 합성 요청 20건을 보내고, 수집 결과에서 누락/중복 없이 각각 추적 가능하다.
- RECORD 이전과 STOP 이후 요청은 해당 recording의 신규 기록에 포함되지 않는다. 경계의 진행 중 요청은 정한 정책대로 표시된다.
- UI 조회를 중단해도 relay 전달이 계속되고 수집 데이터가 보존된다.
- 저장된 packet 목록과 상세를 프로그램 재시작 후에도 조회할 수 있다.
- proxy OFF/오류 시 연결 상태와 오류를 표시하며 다음 실행에 포트/프로세스가 잔존하지 않는다.

의존성: P0, relay를 경유하는 QA 트래픽 경로. P1 완료와 독립적으로 준비할 수 있지만 실제 기기 시험은 겹치지 않는다.

### P3. 평가항목별 Python 점검 스크립트

목적: AI 연결 전에 개별 항목의 검사 절차와 증거·판정 계약을 검증한다.

입력: check ID, device/app 설정, 선행조건, 선택적 route/packet 참조, 합성 또는 QA 시험 설정.
출력: 구조화 결과, 증적 참조, 실행 로그, 정리 결과.

경계:
- E 범주의 한 항목으로 시작하고 항목별로 독립 실행 가능하게 만든다.
- Skill은 검사 절차·판정 기준을 설명하며 Python 도구의 역할과 구분한다.
- 이후 AI가 해당 스크립트를 호출하거나 단계별 도구를 조합할 수 있도록 하되, 모든 항목을 고정 스크립트로만 구현하도록 제한하지 않는다.
- 순정/루팅 여부만으로 자동 판정하지 않는다. 검사하려는 방어 동작과 서비스 이용 결과를 근거로 판단한다.
- U/N 항목은 필요한 동선·패킷·테스트 사용자 조건이 준비된 이후 진행한다.

통과 기준 제안:
- 선택한 첫 항목에서 양호/취약/판단 불가능 각각을 확인할 통제된 fixture 또는 시험 앱 조건을 정의한다.
- 동일 조건을 3회 수행해 동일 판정과 검증 가능한 증적을 얻는다.
- 선행조건 부족은 이유를 포함한 판단 불가능 또는 실행 전 차단으로 표현하며 양호가 되지 않는다.
- 오류/timeout/취소 시 정리 결과를 남긴다.
- 결과 schema 검증과 증적 참조 유효성 검사를 통과한다.

의존성: P0. 첫 E 항목은 가능한 한 P1/P2와 독립적으로 고른다. 동선이나 packet이 필요한 항목에 한해서 P1/P2 산출물을 사용한다.

### P4. 조각 간 통합

목적: 먼저 검증한 조각을 하나의 실행 흐름으로 연결한다.

입력: P1 route, P2 packet, P3 check 도구, 선택 항목, 단일 기기 설정.
출력: 공통 run/session별 통합 이벤트, 결과, 증적.

제안 순서:
1. Python 실행 관리자가 P1/P2/P3를 연결하는 최소 흐름.
2. main AI와 항목별 agent, provider adapter를 연결.
3. GPUI 화면에서 같은 계약으로 상태 조회/명령 전달.
4. 두 번째 모델 백엔드를 연결하여 provider 종속성이 없는지 검증.

통과 기준 제안:
- 입력/패킷/검사 결과가 같은 recording/run 참조로 추적된다.
- 동시 시작 요청을 반복해도 동일 기기에 활성 검사 작업은 최대 1개이다.
- main AI 또는 항목 agent가 멈추면 watchdog이 감지하고 다음 작업의 무조건 시작을 막는다.
- 취소 후 정리가 확인되기 전에는 기기 잠금을 해제하지 않는다.
- 기록 없는 검사, 기록 있는 검사, proxy OFF, 연결 해제 흐름을 각각 재현한다.
- 지원 capability가 동일한 백엔드로 교체할 때 Skill/route/packet/result schema를 수정하지 않는다.

의존성: 해당 통합 시나리오에 필요한 P1/P2/P3의 기준 통과. 독립 PoC가 실패한 부분을 AI나 UI로 감추지 않는다.

## 4. 의존성과 병렬 작업 원칙

문서·fixture 준비는 병렬로 할 수 있다. 실제 기기 사용은 직렬이다.

```text
P0 ──┬─ P1 동선 ────────┐
     ├─ P2 relay ───────┼─ P4 통합
     └─ P3 첫 E 항목 ──┘
         U/N 확장에는 필요한 P1/P2 산출물을 연결
```

P1~P3는 각각 별도 실행 진입점을 갖되 저장소·폴더 배치는 아직 미확정이다. 이 설계 저장소에 실험 코드를 바로 넣을지, 별도 구현 저장소를 만들지는 구현 착수 시 정한다.

## 5. 다음 설계 결정

다음 대화에서는 전체 구현을 시작하기보다 첫 PoC 하나의 실행 명세를 완성한다.

우선 제안은 P1의 'PC에서 입력 → 기록 → Appium 재생' 경로다. 입력 캡처와 재생 가능성이 전체 UX에 영향을 주기 때문이다. 다만 사용자가 정한 E 구현 우선순위는 유지하며, recorder 기반 검증과 E 점검 도구 개발의 순서는 구분한다.

확정할 내용:
- 첫 시험 앱과 재현할 짧은 동선
- 허용 입력 유형, locator/좌표와 대기 방식
- 첫 E 항목의 관찰 범위 및 판정 증거
- 위 제안 수치의 채택 또는 조정

PoC 결과는 성공/실패뿐 아니라 검증한 환경, 재현 절차, 증적, 한계, 계약 변경을 기록한다. 통과 후에만 다음 통합 범위를 늘린다.
