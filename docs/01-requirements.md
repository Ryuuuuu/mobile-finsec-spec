# 01. 제품 요구사항

## 1. 확정된 목적과 범위

실제 모바일 기기를 연결하고 설치된 패키지명 또는 APK/IPA를 입력하여, 선택한 전자금융 평가항목을 AI와 실행 도구로 점검하는 데스크톱 앱이다.

- QA 전용이다. 운영 환경용 기능·승인 절차는 설계하지 않는다.
- Android를 최우선으로 구현하고, iOS와 웹으로 확장한다.
- UI는 Rust + GPUI Kit, recorder/proxy/실행 계층은 Python을 기본 방향으로 한다.
- Appium을 동선 실행에 사용한다. PC에 표시된 기기 화면을 마우스로 조작하는 UX를 허용한다.
- 모델 종속성을 피하고 Claude Code, Codex, 로컬 GLM 등 여러 실행 백엔드를 지원하고자 한다.
- 구현 이전에 명세를 정리하고, 설계 변경은 이 저장소에 commit/push하여 이력을 유지한다.

## 2. 실행 사용자 흐름

1. 연결된 기기를 selectbox에서 선택한다.
2. 대상 패키지명 또는 APK/IPA를 지정한다.
3. 필요한 경우 RECORD를 시작하고 동선을 수행한다.
4. RECORD 동안 UI 입력과 릴레이된 네트워크 데이터를 함께 기록하고 UI에 표시한다.
5. 기록을 종료하고 검사할 평가항목을 체크한다.
6. START로 메인 AI와 항목별 하위 에이전트를 실행한다.
7. 결과와 이유, 실행 이력, 근거를 검토한다.

RECORD 없이도 검사를 시작할 수 있다. 이때 Android 기본 동선은 선택한 패키지를 ADB로 실행하는 것이다. 로그인이나 거래 동선이 필요한 항목까지 충족된 것으로 간주하지 않는다.

## 3. 기기와 점검 선택

- 루팅된 Android와 순정 Android 모두 지원한다.
- 기기는 한 번에 한 대를 대상으로 한다. 기기 작업은 겹치면 안 된다.
- 선택 기기에서 불가능한 항목은 체크 불가 상태로 만들고 이유를 보여준다.
- 항목의 실제 선행조건을 기준으로 비활성화한다. 모든 항목을 단순히 루팅/순정 두 범주로만 나누지 않는다.
- 루팅 탐지 결과, 연결 상태, 플랫폼과 필요한 도구 상태를 preflight에서 확인한다.
- 실행 직전 조건을 다시 검증한다. 기기 연결 해제나 조건 변경을 조용히 무시하지 않는다.

루팅 상태 자동 감지 및 수동 보정, APK 교체 방식과 빌드 일치 검증의 상세는 구현 전 확정한다.

## 4. 결과

판정 값은 다음 세 가지로 한정한다.

- **양호**: 정의한 점검 절차와 기대 방어 동작을 증거로 확인했다.
- **취약**: 정의한 취약 조건을 증거로 확인했다.
- **판단 불가능**: 증거 부족, 선행조건 미충족, 도구/환경 한계 등으로 결론을 낼 수 없다. 이유는 필수다.

실행 실패·중단·미선택과 보안 판정을 구분한다. 검사를 수행하지 못한 상태를 양호로 처리하지 않는다. 팝업 부재만으로 취약, 앱 종료만으로 양호라고 결론 내리지 않는다.

## 5. 구현 우선순위

분류는 **구현 우선순위**이며 모든 실행의 고정 순서를 뜻하지 않는다.

|분류|중점|주요 범위|
|---|---|---|
|E, 1순위|환경·실행 관찰|OS 변조 탐지, 악성코드 대응, 보안프로그램 동작/임의해제, 앱 무결성, 디버깅 탐지|
|S, 2순위|정적 추출·분석|중요정보 노출, 난독화, 보안프로그램 업데이트 관련 분석|
|U, 3순위|UI 재현·입력 변조|거래 인증, 비밀번호 변경 본인확인, 이전 비밀번호 재사용|
|N, 4순위|네트워크 릴레이 기반 점검|거래 무결성, 재사용, 소유주 검증|
|M|수동·증적 보완|자동 판정이 어려운 절차와 운영자 확인 근거|

분류 하나가 도구 하나를 뜻하지 않는다. 예를 들어 업데이트 확인에는 실행 관찰이 필요할 수 있고, UI 기반 항목에도 네트워크 증적이 필요할 수 있다.

## 6. 평가기준 범위 관리

사용자가 제공한 2026 평가기준에서 제목에 [전자금융]이 붙은 항목을 출발점으로 한다. 원문과 평가 예시는 복제하지 않는다.

기존 문서 검토상 해당 18개 제목에는 모바일 식별자가 있는 13개 항목과 HTS 전용 5개 항목이 섞여 있다. 구현 전 합법적으로 보유한 원본으로 항목 식별자와 적용 범위를 최종 대조한다.

모바일 대응 범위는 거래 인증/무결성/재사용/소유주, 비밀번호 변경 본인확인/재사용, OS 변조, 악성코드, 입력정보 보호, 프로그램 무결성, 난독화, 디버깅 탐지, 접근매체 발급 본인확인이다.

보안프로그램 동작/임의해제, 명령줄 평문, HTS 실행 파라미터 재사용, 보안프로그램 업데이트의 모바일 적용은 별도 확장 항목으로 명시한다. 특히 HTS 파라미터 검사를 모바일 공식 평가항목인 것처럼 바꾸지 않는다.

입력정보 보호와 접근매체 발급 절차는 초기 브레인스토밍의 E/S/U/N에 빠져 있었으므로 카탈로그에서 누락하지 않되 자동화 범위와 M 분류 적용을 후속 확정한다.
