# 02. 구조와 오케스트레이션

## 1. 확정된 실행 원칙

START를 누르면 메인 AI가 실행된다. 각 평가항목의 하위 에이전트가 해당 폴더의 공통 및 플랫폼 Skill을 읽고 순차 수행한다. 한 기기의 작업은 중첩하지 않는다. 메인 AI는 종료 여부, hang, 오류를 계속 확인해야 한다.

앱 시작 시 API 서버와 proxy relay 서버가 실행되는 구조다. Proxy는 UI에서 켜고 끌 수 있다. RECORD는 동선과 릴레이 데이터를 동시에 수집하며, 검사 시 관련 데이터를 AI가 활용한다.

## 2. 제안 구조

아래 세부 분리 방식은 v0.1 설계 제안이며 구체 프레임워크와 프로토콜은 미확정이다.

```text
Rust / GPUI Kit
       │
Python API + 실행 관리자 ───── 저장소 / 이벤트 / 감사 로그
       │
       ├─ 메인 AI (백엔드 어댑터)
       │     └─ 평가항목별 하위 에이전트 (순차)
       │
       └─ 공통 Tool Gateway
              ├─ 기기 / 앱 실행 / Appium
              ├─ Recorder / 재생
              ├─ Proxy relay / packet query / replay
              └─ 증적 저장 / 조회

Proxy relay: UI와 AI의 응답 여부와 독립적으로 전달·수집
Watchdog: 메인 AI 및 작업 상태 감시
```

### 책임

- **UI**: 기기 선택, 대상 지정, RECORD/START/취소, 점검 선택, 흐름·패킷·상태·증적 표시.
- **API/실행 관리자**: 큐, 단일 기기 잠금, lifecycle, timeout, 취소, 상태 저장, 복구.
- **메인 AI**: 선택 항목 해석, 순차 실행 지시, 진행·결과 검토, 근거 중심 요약.
- **항목 에이전트**: Skill에 따른 제한된 검사, 도구 호출과 근거 수집, 구조화 결과 제출.
- **Tool Gateway**: 일관된 실행 계약, 잠금 검증, 명령 범위 확인, 입력/결과 감사 기록.
- **Recorder**: 입력 동작과 필요한 화면 상태를 재현 가능한 형태로 기록.
- **Proxy**: 실제 데이터 전달, 수집, 조회, 승인된 QA 시나리오의 변조/재전송 도구.
- **Watchdog**: 메인 AI 자체가 응답하지 않는 경우에도 중단과 상태 보고를 수행.

메인 AI에게 책임만 맡기고 실제 동시성 제어를 프롬프트에만 의존하지 않는다. 임의 shell/ADB 직접 접근이 gateway 잠금을 우회하지 않도록 실행 권한을 설계한다.

## 3. 모델 독립성

Claude Code와 Codex는 에이전트 실행 백엔드이고 GLM은 모델로 사용할 수 있으므로 동일한 수준의 기능을 가진 것으로 가정하지 않는다.

공통 어댑터 계약 제안:
- 작업 시작, 이벤트 수신, 결과 조회, 취소.
- tool 호출, 구조화 출력, 세션 재개 가능 여부 등 capability 선언.
- 백엔드별 인증/실행 방식은 격리.
- Skill, route, packet, evidence, result 형식은 백엔드 밖에 둔다.
- 로컬 모델은 자체 tool loop가 필요할 수 있다.
- SDK/CLI/API 선택, 임베딩 가능 여부와 서비스 약관, 인증 방식, 비용은 구현 전 검증한다.

모든 백엔드에 동일한 재개/취소/구조화 출력 성능을 약속하지 않는다. 지원하지 않는 기능은 명시적으로 capability에 반영한다.

## 4. 순차 실행과 감시

제안 실행 흐름:

1. 연결, 대상, 선택 항목, 관련 route/packet 및 capability 검사.
2. run ID와 설정/Skill 버전 snapshot 생성.
3. 메인 AI 시작.
4. 현재 항목의 기기 잠금 확보.
5. 공통 Skill과 선택 플랫폼 Skill로 항목 세션 실행.
6. 결과 schema 및 증적 참조 검증.
7. 진행 중 도구 종료 확인과 정리.
8. 잠금 해제 후 다음 항목 실행.
9. 판정과 미완료 이유 요약.

제안 상태: queued → preparing → running → cleaning → completed.
failed, timed_out, cancelling, cancelled는 실행 상태이며 판정과 독립이다.

Hang 판단은 프로세스 생존, 마지막 진행 이벤트, 활성 도구, 도구별 timeout, 전체 timeout, 기기 연결을 함께 본다. 출력이 잠시 없다는 이유만으로 hang으로 처리하지 않는다.

취소 시 하위 도구 종료를 확인하고 정리한다. timeout 시간이 지났다고 잠금을 바로 풀고 다음 항목을 실행하지 않는다. 상태 변경 작업은 이전 시도의 결과를 확인한 뒤 재시도한다.

## 5. 확장

Android/iOS/web의 기기 제어와 실행 도구를 adapter로 분리한다. 현재의 최대 3개 Skill은 모바일 단계 기준이며 웹 확장 시 폴더 정책은 별도 변경 결정으로 기록한다.

호스트 OS 지원 범위는 미확정이다. Windows 우선 UI 개발과 iOS 제어에 필요한 호스트/개발 도구 제약을 별도로 검증한다.
