# P3 CHK-07: 정상·변조 QA 기기 비교 재개 명세

이 문서는 E 환경 점검의 **OS 변조 탐지** 항목에 대한 실기기 재개 준비입니다. 내부 CHK-07 매핑이며 공식 평가 원문의 식별자·버전 대응 확정이나 인증 적합 판정이 아닙니다. 현재 실행한 것은 합성 fixture와 로컬 코드 시험뿐입니다. 기기 수집·앱 실행·변조·복원은 수행하지 않았습니다.

## 비교 전 준비

1. 승인된 전용 정상 QA 기기와 사전에 준비된 변조 QA 기기를 지정합니다. 이 POC는 기기를 루팅하거나 보안 정책을 변경하지 않습니다. 시험 권한·앱·빌드·서비스 범위와 재개 시점의 승인을 확인합니다. 과거 승인만으로 추가 변경을 수행하지 않습니다.
2. 정상 기기의 제조사/관리자 provisioning 기록과 변조 QA 기기의 허용된 준비 기록, 이미지·빌드 기준, 검증 주체·시각·유효 기간을 비공개 증거에 연결합니다. getprop, su 흔적, shell id, SELinux 상태 등은 보조 관찰이며 독립적인 상태 증명으로 취급하지 않습니다. 출처·무결성·신뢰성 검토가 없으면 상태는 unknown입니다. 해시는 진실성 인증이 아닙니다.
3. 동일 앱 패키지·APK 빌드 해시·설정·보호 서비스·checkpoint를 고정합니다. OS 버전, 기종, 네트워크, 앱 상태, 시간 등 다른 차이와 통제하지 못한 교란 요인을 기록합니다. 원인 분리가 불가능하면 판단 불가능으로 남깁니다.
4. 개인정보 없는 합성 QA 데이터와 실제 거래가 없는 checkpoint를 사용합니다. 정상 baseline에서 서비스 이용 완료를 확인한 후 변조 QA 기기에서 동일 checkpoint를 관찰합니다. 앱 시작·로그인 화면 표시만으로 보호 서비스 이용을 인정하지 않습니다.
5. 차단 oracle은 앱의 명시적인 OS 변조 사유, 해당 정책/서비스와 대응하는 QA 계측 및 동시점 관찰을 함께 정의합니다. 단순 팝업, 프로세스 종료, HTTP 실패, 타임아웃, 네트워크 오류는 차단 원인 증거가 아닙니다. 앱이 종료되어도 보안 탐지 성공을 추정하지 않습니다.

## 수집 순서와 증거 계약

- 시험 전 두 역할의 연결·잠금/승인 상태, 공유 device lease, 미해결 cleanup/quarantine, 기존 보안 설정 baseline 및 사용자 유지 지시를 확인합니다. 이것은 앞으로의 절차이며 이번 준비 작업에서는 조회조차 수행하지 않았습니다.
- lease 하에서 연결 상태를 다시 확인합니다. 준비표의 `device` 값은 순간적인 선언이며 최신 연결을 보증하지 않습니다. 허용된 read-only probe는 환경 관찰만 하고 항상 inconclusive를 유지합니다.
- run/attempt/phase/scope/기기 역할별로 증거를 분리하고 package/build/service/checkpoint, 수집 시각·순서·관찰 방법, 바이트 해시, oracle 판단 근거를 연결합니다. 실제 식별자·화면·앱 로그·환경 상세는 비공개 보관합니다. 공개 문서에는 합성 데이터와 집계만 남깁니다.
- 정상 서비스 baseline과 변조 상태·서비스 결과를 서로 다른 증거로 연결합니다. 서로 다른 build/checkpoint나 이전 attempt의 stale 증거를 섞지 않습니다. 순서·시각 불일치나 상충 증거는 해당 scope를 판단 불가능으로 처리합니다.

|근거|해당 scope 판정|
|---|---|
|정상 상태·서비스 이용, 변조 상태, 같은 서비스의 OS 변조 원인 차단이 모두 충분|정의된 scope에서 양호 후보; 실증거 어댑터/검토 구현 전 실제 자동 판정 금지|
|정상 baseline과 변조 상태가 충분하고 동일 보호 서비스 이용이 확인|정의된 scope에서 취약 후보; 실제 운영 거래 수행 금지|
|루팅 지표만 있음, 상태 근거 누락, crash/launch만 관찰, 원인 불명 차단, build 불일치, 상충 근거|판단 불가능|

기존 합성 엔진은 위 조건을 fixture로 모델링하며 pass/fail을 생성할 수 있습니다. 이는 앱/기기에서 실제 확인한 결과가 아닙니다. 일관된 scope의 취약 근거가 이미 있으면 이후 다른 scope의 timeout/cleanup 실패가 이를 없애지 않습니다. 동시에 미완료 scope와 실행 오류를 반드시 보존합니다. 동일 scope의 상충 관찰을 다수결로 무시하지 않습니다.

## 연결 해제·오류·재개

- 시작 전 offline/unauthorized/미확인: not_run, 실행하지 않고 필요한 사용자 조치를 보고합니다. RSA 승인이나 팝업을 자동 처리하지 않습니다.
- 진행 중 끊김/도구 오류/timeout/cancel: 후속 명령을 멈추고 부분 근거, 마지막 성공 단계, 오류 범주를 기록합니다. 실행 실패를 보안 취약이나 탐지 성공으로 변환하지 않습니다. 도구의 원문 오류에 식별자가 포함될 수 있으므로 공개하지 않습니다.
- 기기를 조작하지 않은 사용자의 경우에도 원인을 단정하지 않습니다. 연결 해제 사실과 원인 추정을 구분하고 이전 관찰을 현재 연결 상태로 재사용하지 않습니다.
- 자동 reconnect 후 동선 재실행·설정 변경은 하지 않습니다. 새 attempt에서 연결, lease, 소유 자원, 미해결 cleanup, 기존 유지 설정, 앱 상태를 확인합니다. 실제 상태를 확인하지 못하면 복원 실패가 아니라 **복원 미확인**으로 기록합니다.
- cleanup failed/unknown이면 후속 실행 차단·수동 검토 필요. 이 gate 자체는 lease를 획득하거나 외부 작업자를 막지 않으므로 실행 통합에서 강제해야 합니다. 기존 사용자 유지 지시를 자동 복원으로 덮어쓰지 않습니다.

## 구현과 기기 없는 검증

`resume_gate.py`는 11개 준비 항목, 두 역할의 연결 선언, cleanup 상태를 엄격한 유한 스키마로 검토하는 순수 함수입니다. 알 수 없는 키·문자열 boolean을 거부합니다. 출력은 blocked 또는 ready_for_manual_review이며 **항상 verdict=inconclusive, device_execution=not_run, auto_resume=false**입니다. 준비 완료가 실행 허가나 증거 진실성 확인은 아닙니다. 입력/출력에는 장치 식별자나 원문 증거를 넣지 않습니다.

```powershell
# pocs/p3-android-os-tamper 디렉터리, 기존 venv
python -m unittest discover -s tests -v
```

`tests/test_resume.py`는 모든 누락 gate, 양쪽 연결 상태, cleanup, 엄격한 입력, 무변경 함수 동작과 기존 엔진의 정상/취약/불충분 비교를 검증합니다. 실기기 두 대 비교, 변조 준비·attestation 검증, 앱의 실제 차단 oracle, 실제 끊김 후 재개, 제품 GUI 연동은 아직 미검증/미구현입니다. 실기기 재개 전에 이 공백과 허용 QA 대상부터 확정해야 합니다.

검증 기록(2026-11-18): P3 전체 85개 시험 중 84개 통과, 기존 Windows 권한 관련 1개 건너뜀. 신규 12개 시험은 모두 통과했습니다. 기존 read-only adapter 시험은 stub/mock으로 실행했고 실제 ADB/기기 수집은 실행하지 않았습니다. 로그는 비공개 작업 폴더에 보관했습니다.
